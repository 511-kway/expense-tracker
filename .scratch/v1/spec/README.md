# Трекер затрат: документация для разработки

Версия 1 (MVP). Дата: 2026-11-03.

Это комплект спецификаций для реализации силами ИИ агентов (spec driven development). Личное приложение для учёта затрат семьи и расчётов с компанией. Веб кабинет первым, мобилка позже.

## Как пользоваться этим комплектом

Это источник правды. Пиши код строго по этим докам. Если по ходу находишь пробел или противоречие, не додумывай молча: предложи правку спеки, зафиксируй решение, потом кодь.

## Порядок чтения

1. `00-overview.md` — что это, цели, рамки, глоссарий. Прочитать первым.
2. `01-architecture.md` — стек, почему не Node, авторизация, хостинг, безопасность.
3. `02-data-model.md` — таблицы, поля, enum, индексы, связи. Основа.
4. `03-engine-and-operations.md` — движок расчёта, эффект каждой операции, реплей, edge cases. Самый важный.
5. `04-functional-spec.md` — функционал по областям, поведение без визуала.
6. `05-api.md` — RPC-функции, представления, Edge Functions, коды ошибок.
7. `06-testing.md` — стратегия и конкретные тест-кейсы с числами.

Визуал (экраны, вёрстка) в этот круг не входит, прорабатывается отдельно. Прототипы существуют как референс.

## Главные принципы (не нарушать)

1. **Баланс не хранится числом.** Остаток, аванс и долг выводятся из журнала `ledger_entries`. Любое изменение пересобирает ledger через `recompute`.
2. **Вся денежная логика на сервере.** Движок это функции Postgres в транзакции. Клиент только собирает ввод, зовёт RPC, показывает результат. Никаких денежных вычислений и прямых записей в `entries`/`ledger_entries` с клиента.
3. **Деньги целыми** в минимальных единицах (тиыны). Без float.
4. **Аванс считается по реальной дате** операции, с хронологическим реплеем. Запись задним числом корректна за счёт recompute.
5. **Нет Node как рантайма.** Supabase self hosted плюс функции Postgres плюс Edge Functions на Deno. Node только dev-сборка фронта.

## Порядок реализации (вехи)

Делать итерациями, каждая с тестами, которые зелёные перед следующей.

1. **Схема и движок.** Миграции: таблицы, enum, индексы, RLS (док 02). Функции Postgres: `create_entry`, `update_entry`, `delete_entry`, `recompute`, валидация (доки 03, 05). Представления (`v_account_balances`, `v_company_settlement`, `v_settlement_breakdown`, `v_overview`). Юнит-тесты движка (док 06, разделы 3 по 10) зелёные.
2. **Авторизация и справочники.** Google OAuth через GoTrue. CRUD счетов (с guard архива) и категорий. Сиды справочников владельца.
3. **Ввод операций.** RPC и формы: полная запись, быстрый capture (draft), инбокс, promote_draft. Живой предпросмотр эффекта (считает по правилам движка).
4. **Заметки и вложения.** Storage, заметки, convert_note_to_entry.
5. **Импорт и экспорт.** Edge Function парсинга, import_preview/commit (атомарно, дедуп, идемпотентность), экспорт по единой схеме. Тесты раздела 11.
6. **Валюта.** Edge Function курсов Нацбанка, таблица `fx_rates`, три способа пересчёта. Тесты раздела 10.
7. **Claude Code ingestion.** Защищённый вход создания записей.
8. **Обзор и баланс с компанией.** Агрегаты и раскрытие долга.

Мобилка (Flutter, виджет быстрого capture) и встроенная аналитика это отдельный круг после MVP.

## Определение готового (definition of done) для каждой задачи

- Код соответствует спеке.
- Тесты по доку 06 для затронутой области написаны и зелёные.
- Инварианты (док 03, раздел 10) проверяются в тестах.
- Миграции применяются на чистую базу одной командой.
- RLS на месте для новых таблиц.
- Нет денежной логики на клиенте.

## Тесты и ревью (сейчас и дальше)

- Тесты пишутся вместе с кодом по доку 06. Движок покрывается в первую очередь.
- CI прогоняет миграции и тесты на чистой базе. Зелёные тесты условие мёржа.
- Позже добавляется ai code reviewer в CI (проверка спека-соответствия, безопасности RLS, отсутствия логики на клиенте). Его правила выведутся из этих доков.

- Решено при реализации тикета 03 (2026-11-04): пример `$1 200,00` в доке 04 противоречил правилу «копейки только если не нулевые», исправлен на `$1 200`. - Решено при реализации тикета 04 (2026-11-04): владелец из `ADMIN_EMAIL` разрешается не SQL-сидом (он не читает env), а `scripts/allow-owner.sh` через RPC `allow_owner(email)` (только service_role); его зовут `dev-up.sh`, `db-reset.sh` и будущий деплой. RLS каждой таблицы с данными ставится одной функцией `apply_user_rls(table)` (политика `user_id = auth.uid() and is_allowed()`), страж-тест `900_rls_guard` ловит таблицу с `user_id` без неё. Для RPC есть `assert_allowed()` (ошибка `not_allowed`). `register_login()` без email в JWT даёт `not_authenticated`; зовётся при каждом открытии приложения с сессией, поэтому `attempts` у владельца это число открытий. Для локальной разработки без Google-ключей добавлен вход по ссылке из письма (Mailpit), только в `vite dev` с `VITE_DEV_EMAIL_LOGIN=true`; лист ожидания действует и для него.
- Решено при реализации тикета 05 (2026-11-04): ошибка RPC приходит как `message` = код из дока 05, `details` = JSON (`entry_id`, `occurred_on` и подробности для ошибок реплея). Новые коды: `amount_negative` (стартовый долг меньше нуля; ноль можно), `debt_below_zero` (долговая корректировка уводит сторону в минус, текст «Сторона долга не может уйти в минус»), служебный `entry_type_not_supported` (тип ещё не реализован в движке). Строка `user_settings` создаётся только `setup_start`, её наличие = «первый запуск пройден». Нулевая сторона стартового долга записи не создаёт. Параметры `setup_start` с префиксом `p_` (как `allow_owner`), дата по умолчанию сегодня по Алматы. `amount_kzt_minor` обязателен только у учтённой записи (черновик может ждать курса). FK `entries` на счета, категории, заметки и партии импорта добавляют тикеты, где появляются эти таблицы. Движок живёт в схеме `engine`, наружу только RPC.
- Решено при реализации тикета 06 (2026-11-04): стартовый остаток это две корректировки остатка на дату старта: «всего − компании» без аванса и «из них компании» с `adjustment_affects_advance` (по формуле дока 03, 4.7 корректировка с авансом двигает и остаток, поэтому «остаток на всего» плюс аванс дало бы лишнее). Корректировка остатка с авансом в минус режет аванс на нуле, остаток уменьшается на всю сумму. Название счёта уникально у пользователя (`account_name_taken`, импорт сопоставляет по точному названию). Счета правятся только через RPC (`update_account`: название, банк, маска, валюта; тип и дата старта не меняются), прямой записи в `accounts` у клиента нет. Удалить можно счёт без записей (черновики тоже записи). Новые коды: `account_name_taken`, `opening_advance_too_big` (компании больше, чем всего), `foreign_opening_not_supported` (стартовый остаток валютного счёта пока только нулевой: тенговый эквивалент и аванс в тенге придут с тикетом 14), `start_not_set` (счёт до первого запуска), `currency_invalid`. «Свои» в форме создания считает сервер (`preview_account_opening`), клиент не вычитает. `v_account_balances` дополнительно отдаёт `mask`, `start_date`, `has_entries`. FK записей и журнала на счета составные `(user_id, account_id)`.
- Решено при реализации тикета 07 (2026-11-04): RPC записей `create_entry(p_payload)`, `update_entry(p_entry_id, p_payload)`, `delete_entry(p_entry_id)` → `{ok, entry_id, status, warnings}`; поля payload, которые не относятся к типу записи, отбрасываются (правка со сменой типа очищает поля старого типа). Сумма в payload только целым числом JSON, иначе `field_invalid` (`{field}`). Источник личной траты: если не задан и на счёте на момент траты аванса нет, сервер ставит «свои» и хранит; если аванс есть, ошибка `source_required` (`{account_id, advance_minor}`). Форма спрашивает сервер `expense_source_needed(p_account_id, p_occurred_on, p_entry_id)`, нужен ли вопрос. У рабочей траты `source` пустой, сплит виден в журнале и в ленте `v_entries` (дельты остатка, аванса и сторон долга по записи). Предупреждение `negative_balance` выдаётся, когда запись уводит остаток счёта из нуля или плюса в минус (`{entry_id, occurred_on, account_id, balance_minor}`); пересчёт отдаёт все такие места истории, экран показывает одно на счёт. Мягкий дубль `possible_duplicate` (`{entry_id, duplicate_of, occurred_on}`): учтённая запись с тем же отпечатком (тип, дата, счёт, сумма, валюта, заголовок или категория). Пока нет валюты (тикет 14), запись только в тенге на тенговый счёт, иначе `foreign_amount_not_supported`; черновики только с быстрым вводом (тикет 15), до него `status = draft` даёт `entry_status_not_supported`. Категории только через RPC (`create_category`, `rename_category`, `archive_category`, `unarchive_category`), название уникально без учёта регистра (`category_name_taken`); категорию с записями не удалить (FK restrict), удаления категорий нет. Новые коды: `field_invalid`, `source_required`, `foreign_amount_not_supported`, `entry_status_not_supported`, `entry_not_found`, `category_name_taken`.
- Решено при реализации тикета 09 (2026-11-04): пополнение от компании: банк удерживает комиссию из отправленного (пришло = отправила − комиссия); `amount_minor` = отправленное, если комиссию платил я (ADR-0003, компания засчитывает всё), иначе пришедшее. Три способа ввода комиссии: «пришло и комиссия», «отправила и комиссия», «отправила и пришло»; суммы считает сервер (`topup_amounts`), не клиент. При комиссии плательщик обязателен, без комиссии не хранится; своя комиссия должна быть меньше суммы (`fee_too_big`, текст «Комиссия должна быть меньше суммы пополнения»), отрицательная комиссия `amount_negative`. «Изъятие не больше аванса» проверяет только пересчёт: `advance_return_too_big` с `entry_id` конфликтного изъятия, `account_id`, `advance_minor`, `amount_minor`; текст «Изъять можно не больше аванса на счёте на эту дату» (слово «вернуть» по `GLOSSARY.md` не используем). Форме изъятия аванс на дату отдаёт `advance_on_date`.
- Решено при реализации тикета 10 (2026-11-04): комиссия перевода всегда списывается с «откуда»; компания съедает аванс «откуда» до нуля (нехватка из своих, долг не трогается), моя только остаток. Комиссия применяется раньше назначения: перекладка аванса переносит аванс, оставшийся после комиссии. «Погашение долга в аванс не больше долга» проверяет только пересчёт: `debt_overpay` `{entry_id, occurred_on, side, available_minor, amount_minor}` с id конфликтного погашения. «Куда» в форме: без «откуда» и только счета той же валюты. Лента `v_entries`: дельты остатка и аванса по «откуда», у перевода плюс `to_*` по «куда»; форме долг на дату отдаёт `debt_on_date`. Доки 02 и 03 ещё упоминают `top_up_advance`: его нет (spec.md).
- Решено при реализации тикета 11 (2026-11-04): погашение долга (`settlement`) требует счёт (`missing_required`, `account_id`) и направление (`settlement_direction`); «я отдал компании» = остаток минус, «я должен компании» минус; «компания отдала мне» = остаток плюс как свои (аванс не меняется), «компания должна мне» минус. Больше стороны на дату ловит только пересчёт: `debt_overpay` с `side` и id конфликтного погашения. Взаимозачёт (`netting`): без счёта (присланный `account_id` отбрасывается), только в тенге, обе стороны минус сумма; больше меньшей стороны на дату: новый код `netting_too_big` `{entry_id, occurred_on, available_minor, company_owes_me_minor, i_owe_company_minor, amount_minor}`, текст «Взаимозачёт не больше меньшей стороны долга»; проверяет только пересчёт. Выборка `v_settlement_breakdown`: строка = запись × сторона долга, с `delta_minor` и `side_after_minor` (сторона после записи в порядке пересчёта). На экране «Расчёт с компанией» список «Погашения и взаимозачёты» включает и переводы «погашение долга в аванс»: это тоже погашение. Упоминания `top_up_advance` в доках 02 и 03 заменены пометкой со ссылкой на spec.md; в доке 02 счёт погашения обязателен, в доке 03 описан взаимозачёт (4.6a), в доке 05 добавлен `netting_too_big`.
