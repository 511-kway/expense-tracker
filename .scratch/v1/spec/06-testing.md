# 06. Документация по тестам

Версия 1. Дата: 2026-11-03.

Цель: чтобы ИИ агент написал тесты сразу по этому документу. Здесь стратегия и конкретные тест-кейсы с числами и ожидаемым результатом. Все суммы в тенге; в коде умножай на 100 (тиыны).

## 1. Уровни тестов

1. **Юнит на движок (главное).** Тесты функций Postgres (создание операций и `recompute`). Инструмент: pgTAP или интеграционные тесты через supabase-js, вызывающие RPC на тестовой базе. Каждый тест: задать набор операций, вызвать движок, проверить счётчики через представления (`v_account_balances`, `v_company_settlement`).
2. **Интеграционные на RPC.** Проверяют валидацию, коды ошибок, атомарность, идемпотентность импорта, RLS (пользователь не видит чужое).
3. **Тесты инвариантов.** После любого сценария проверять инварианты (раздел 10 дока 03): аванс ≥ 0, долговые счётчики ≥ 0, итог = разница сторон.
4. **E2E и фронт (позже, не в первом круге).** Минимальные smoke-тесты UI.

## 2. Фикстуры

Базовый набор для большинства тестов (каждый тест стартует с чистой базы и этих справочников):
- Счета (все KZT, если не сказано иное): `H1` (Халык 1), `H2` (Халык 2), `KS` (Kaspi свой), `KP` (Kaspi Pay), `CASH` (наличные).
- Категории: `Реклама`, `Аптека`, `Продукты`, `Питание`.
- Старт: все остатки 0, авансы 0, долги 0.

Каждый тест описывается как список операций (в порядке реальных дат), затем ожидаемые значения после `recompute`. Если даты не указаны, считать операции одним днём в порядке перечисления (tiebreak по `seq`).

Обозначения в ожиданиях: `adv[X]` аванс счёта, `bal[X]` остаток, `owe_me` = company_owes_me, `i_owe` = i_owe_company, `net` = owe_me − i_owe.

## 3. Тесты типов операций

### TC-TOPUP-1 (пополнение)
Операции: topup H1 landed=100000 fee=0.
Ожидание: adv[H1]=100000, bal[H1]=100000, owe_me=0, i_owe=0.

### TC-TOPUP-FEE-OWN (ты платишь комиссию из своих, ADR-0003)
Операции: income H1 10000; topup H1 landed=100000 fee=500 fee_payer=own.
Ожидание: bal[H1]=109500, adv[H1]=100000, owe_me=500, i_owe=0, net=+500.

### TC-TOPUP-FEE-OWN-OFFSET (возмещение комиссии сначала гасит мой долг)
Операции: topup H1 100000; expense personal H1 300 source=company (i_owe=300, adv=99700); income H1 10000; topup H1 landed=50000 fee=500 fee_payer=own.
Ожидание: bal[H1]=159200, adv[H1]=149700, i_owe=0, owe_me=200, net=+200.

### TC-TOPUP-FEE-OWN-SHORT (своих не хватает, нехватка из аванса)
Операции: topup H1 100000 (свои на H1 = 0); income H1 300; topup H1 landed=99000 fee=1000 fee_payer=own.
Ожидание: own_part=300, co_part=700. bal[H1]=198300, adv[H1]=198300, owe_me=300, i_owe=0.

### TC-EXP-WORK-WITHIN (рабочая в пределах аванса)
Операции: topup H1 100000; expense work H1 60000.
Ожидание: adv[H1]=40000, owe_me=0, bal[H1]=40000.

### TC-EXP-WORK-SPLIT (рабочая больше аванса, авто-сплит)
Операции: topup H1 60000; expense work H1 100000.
Ожидание: adv[H1]=0, owe_me=40000, bal[H1]=-40000.
(Отрицательный остаток в синтетическом тесте допустим, это не ошибка движка.)

### TC-EXP-PERS-COMPANY (личная деньгами компании)
Операции: topup H1 100000; expense personal H1 30000 source=company.
Ожидание: adv[H1]=70000, i_owe=30000, bal[H1]=70000.

### TC-EXP-PERS-COMPANY-SPLIT (личная деньгами компании больше аванса)
Операции: topup H1 20000; expense personal H1 50000 source=company.
Ожидание: adv[H1]=0, i_owe=20000, bal[H1]=-30000. (own_part 30000 нейтрально.)

### TC-EXP-PERS-OWN (личная своими)
Операции: income H1 50000; expense personal H1 20000 source=own.
Ожидание: adv[H1]=0, i_owe=0, owe_me=0, bal[H1]=30000.

### TC-EXP-OWN-WORK (рабочая своими, аванса нет)
Операции: income H1 50000; expense work H1 20000.
Ожидание: owe_me=20000, adv[H1]=0, bal[H1]=30000.

### TC-INCOME (поступление)
Операции: income KS 250000.
Ожидание: bal[KS]=250000, owe_me=0, i_owe=0, adv[KS]=0.

## 4. Тесты переводов

### TC-TRANSFER-REPAY (погашение долга)
Операции: topup H1 100000; expense personal H1 30000 source=company (теперь i_owe=30000, adv=70000); transfer repay_debt from KS to H1 amount=30000.
Ожидание: i_owe=0, adv[H1]=100000, bal[KS]=-30000, bal[H1]=70000+30000=100000.

### TC-REPAY-CAP (погашение больше долга → ошибка)
Операции: как выше, но repay_debt 50000 при i_owe=30000.
Ожидание: ошибка `debt_overpay`, состояние не изменилось.

### TC-MOVE-COMPANY (перекладываю деньги компании)
Операции: topup KP 60000; transfer move_company KP→H1 60000.
Ожидание: adv[KP]=0, adv[H1]=60000.

### TC-MOVE-COMPANY-PARTIAL (аванса меньше суммы)
Операции: topup KP 40000; transfer move_company KP→H1 60000.
Ожидание: adv[KP]=0, adv[H1]=40000. (остаток 20000 свои, нейтрально)

### TC-TAKE-ADVANCE (взял аванс себе на личное)
Операции: topup H1 100000; transfer take_advance H1→KS 30000.
Ожидание: adv[H1]=70000, i_owe=30000.

### TC-MOVE-OWN (перекладываю свои)
Операции: income KS 50000; transfer move_own KS→H1 50000.
Ожидание: adv без изменений, bal[KS]=0, bal[H1]=50000, долги 0.

### TC-SAME-ACCOUNT (перевод на тот же счёт → ошибка)
Операции: transfer KS→KS 1000.
Ожидание: ошибка `same_account_transfer`.

## 5. Тесты взаимозачётов

### TC-SETTLE-IPAID (я вернул компании)
Операции: topup H1 100000; expense personal H1 30000 source=company (i_owe=30000); settlement i_paid_company 30000 account=KS.
Ожидание: i_owe=0, bal[KS]=-30000.

### TC-SETTLE-CAP (вернул больше долга → ошибка)
Операции: как выше, но settlement 50000 при i_owe=30000.
Ожидание: ошибка `debt_overpay`.

### TC-SETTLE-COMPANY-PAID (компания вернула мне)
Операции: income H1 50000; expense work H1 20000 (owe_me=20000); settlement company_paid_me 20000 account=H1.
Ожидание: owe_me=0, bal[H1] += 20000.

## 6. Возврат аванса компании

### TC-ADV-RETURN
Операции: topup H1 100000; company_advance_return H1 60000.
Ожидание: adv[H1]=40000, bal[H1]=40000, долги 0.

### TC-ADV-RETURN-CAP
Операции: topup H1 100000; company_advance_return H1 120000.
Ожидание: ошибка `advance_return_too_big`.

## 7. Корректировки

### TC-ADJUST-HIDDEN (plug вне аналитики)
Операции: income H1 100000; adjustment H1 sign=-1 amount=18300 mode=plug_hidden.
Ожидание: bal[H1]=81700, долги и аванс без изменений, запись с in_analytics=false (не попадает в личные траты).

### TC-ADJUST-ADVANCE (plug по авансу)
Операции: topup H1 100000; adjustment H1 sign=-1 amount=5000 affects_advance=true.
Ожидание: adv[H1]=95000, bal[H1]=95000.

## 8. Возвраты (refund)

### TC-REFUND-FULL
Операции: topup H1 100000; expense personal H1 30000 source=company (adv=70000, i_owe=30000, bal=70000); refund parent=этой траты amount=30000.
Ожидание: adv[H1]=100000, i_owe=0, bal[H1]=100000. (полный откат)

### TC-REFUND-PARTIAL
Операции: как выше, refund 15000.
Ожидание: adv[H1]=85000, i_owe=15000, bal[H1]=85000.

### TC-REFUND-CAP
Операции: как выше, refund 40000 при исходной 30000.
Ожидание: ошибка `refund_too_big`.

## 9. Главный тест: порядок и реплей

### TC-BACKDATE-NET (итог не зависит от порядка ВВОДА, зависит от реальной даты)
Операции (реальные даты):
- 2026-01-01: expense work H1 100000 (в этот момент аванса нет).
- 2026-01-10: topup H1 100000.
Вводим их в ЛЮБОМ порядке (например, topup внесён в систему первым, трата задним числом второй).
Ожидание: owe_me=100000, adv[H1]=100000, net=+100000.
Смысл: трата 1 января списать аванс не могла (его ещё не было), значит компания должна тебе 100000, и отдельно лежит аванс 100000. Итог НЕ схлопывается в ноль.

### TC-REALDATE-CONSUME (обратный порядок дат схлопывает)
Операции (реальные даты):
- 2026-01-01: topup H1 100000.
- 2026-01-10: expense work H1 100000.
Ожидание: owe_me=0, adv[H1]=0.
Смысл: к 10 января аванс был, трата его съела. Сравнение с предыдущим тестом доказывает, что считаем по реальной дате.

### TC-TIEBREAK (детерминизм в один день)
Операции одной датой 2026-02-01, в порядке seq:
1. topup H1 50000
2. expense work H1 30000
3. expense work H1 40000
Ожидание: после op2 adv=20000; op3: company_part=20000, own_part=20000 → owe_me=20000, adv=0.
Повторный `recompute` на тех же данных даёт тот же результат (идемпотентность).

### TC-RECOMPUTE-IDEMPOTENT
Любой сценарий: вызвать `recompute` дважды подряд. Второй вызов не меняет счётчики.

### TC-EDIT-RECOMPUTE (правка пересчитывает)
Операции: topup H1 100000; expense work H1 60000 (adv=40000). Затем update суммы траты на 20000.
Ожидание: adv[H1]=80000. (ledger пересобран)

### TC-DELETE-RECOMPUTE (удаление пересчитывает)
Операции: как выше, затем delete траты.
Ожидание: adv[H1]=100000.

### TC-BACKDATE-DELETE-GUARD (удаление задним числом не уводит долг в минус, ADR-0006)
Операции: 2026-03-01 topup H1 100000; 2026-03-02 expense personal H1 30000 source=company (i_owe=30000); 2026-03-05 settlement i_paid_company 30000 account=KS. Затем delete траты от 03-02.
Ожидание: ошибка `debt_overpay` (settlement 03-05 стал бы больше долга), трата не удалена, состояние прежнее.

### TC-BACKDATE-INSERT-GUARD (вставка задним числом до погашения)
Операции: 2026-03-01 topup H1 100000; 2026-03-02 expense personal H1 30000 source=company; 2026-03-03 settlement i_paid_company 30000. Затем create settlement i_paid_company 10000 датой 2026-03-02 (после траты).
Ожидание: ошибка `debt_overpay` на операции 03-03 (к ней долг 20000 < 30000), ничего не создано.

### TC-REFUND-ROUNDING (дробный сплит, без дрейфа)
Операции: topup H1 100.01; expense personal H1 300.00 source=company (company_part=10001 тиын, adv=0, i_owe=100.01); refund 100.00; refund 100.00; refund 100.00.
Ожидание после всех трёх: adv[H1]=10001 тиын, i_owe=0, bal[H1]=10001 тиын (полный откат точно). После первого: adv восстановлен на floor(10001·1/3)=3333 тиына.

## 10. Валюта

### TC-FX-NBK (трата в долларах по курсу Нацбанка)
Фикстура: курс USD на дату = 480. Операция: expense work H1 amount=100 USD, rate_source=nbk.
Ожидание: amount_kzt=48000; движок считает по 48000 тенге. bal[H1] уменьшается на 48000 (тенге, это валюта счёта). adv/owe_me считаются в тенге по 48000.
(Правило: дельта остатка в валюте счёта. H1 тенговый, значит списывается тенговый эквивалент 48000, а не 100.)

### TC-FX-MANUAL / TC-FX-DERIVED
Те же, но rate_source=manual (курс вручную) и derived (введена сумма в тенге, курс выведен). Проверить, что amount_kzt берётся корректно и движок использует тенге.

## 11. Дедуп и импорт

### TC-DEDUP-IMPORT
Импорт двух одинаковых строк (та же дата, счёт, сумма, тип, описание).
Ожидание: вторая помечена возможным дублем в предпросмотре, при коммите не создаётся молча (или создаётся по решению пользователя, но флаг стоит).

### TC-IDEMPOTENT-IMPORT
Импорт файла с external_id, затем повторный импорт того же файла.
Ожидание: во второй раз строки с теми же external_id пропущены (`skipped`), дублей нет.

### TC-IMPORT-ATOMIC
Импорт партии, где одна строка невалидна (несуществующий счёт).
Ожидание (ADR-0004): вся партия откатывается, в `entries` и `ledger_entries` 0 новых строк, черновики не созданы, `import_batches.status = failed`, отчёт указывает ровно на невалидную строку с кодом `account_not_found`.

## 12. Guard и RLS

### TC-ARCHIVE-GUARD
Архив счёта с adv>0 или bal≠0 → ошибка `archive_nonzero`.

### TC-DELETE-ACCOUNT-GUARD
Удаление счёта с операциями → ошибка `account_delete_forbidden`.

### TC-CURRENCY-LOCK
Смена валюты счёта, по которому есть операции → ошибка `account_currency_locked`.

### TC-RLS
Пользователь A не видит и не меняет данные пользователя B (чтение и запись).

### TC-WAITLIST
Вход с незнакомым email: строка в `app_users` с `allowed = false`, `register_login` → `allowed = false`, любая RPC → `not_allowed`, чтение таблиц пусто. Тот же email после `allowed = true` работает.

## 12a. Старт и даты (ADR-0008)

### TC-OPENING
setup_start(2026-11-01, owe_me=12000, i_owe=5000); create_account H1 start=2026-11-01 total=150000 company=100000.
Ожидание: bal[H1]=150000, adv[H1]=100000, own[H1]=50000, owe_me=12000, i_owe=5000, net=+7000. Личные траты за период = 0 (стартовые записи вне аналитики).

### TC-BEFORE-START
Как выше, затем expense H1 датой 2026-10-31.
Ожидание: ошибка `entry_before_start`. То же для взаимозачёта (netting, без счёта) датой раньше accounting_start_date.

### TC-QUICK-CAPTURE (ADR-0009)
create_account H1 total=100000 company=50000; KS total=10000 company=0.
- быстрый ввод work H1 1000 → done.
- быстрый ввод personal KS 500 без категории → done, source=own, в инбоксе «без категории».
- быстрый ввод personal H1 700 → draft, source_pending=true, на счётчики не влияет.

## 13. Инварианты (проверять в каждом сценарии)

После `recompute` в любом тесте дополнительно проверять:
- Для каждого счёта adv ≥ 0.
- owe_me ≥ 0, i_owe ≥ 0.
- net = sum(owe_me) − sum(i_owe).
- Сумма всех дельт balance по счёту равна значению `v_account_balances.balance_minor`.

## 14. Как запускать

- Юнит и интеграционные на эфемерной базе: поднять Supabase локально (CLI), применить миграции и сиды, прогнать тесты, обнулять между тестами (truncate пользовательских таблиц или транзакция с откатом на тест).
- CI: тот же прогон на чистой базе из миграций. Зелёные тесты это условие мёржа (сюда же позже встанет ai code reviewer).
