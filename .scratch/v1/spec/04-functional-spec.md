# 04. Функциональная спецификация

Версия 1. Дата: 2026-11-03.

Функционал по областям, без визуала. Описывает, что система делает и как себя ведёт. Экраны и вёрстка проектируются отдельно; здесь только поведение и правила.

## 1. Авторизация

- Вход только через Google. Нет пароля, нет регистрации вручную.
- После входа сервер записывает попытку в `app_users`. Если `allowed = false`, показывается «Добавили вас в лист ожидания» и сессия завершается. Пускается только `allowed = true` (владелец из `ADMIN_EMAIL` в `.env`). Разрешение выдаётся руками в Supabase Studio (ADR-0007).
- После входа пользователь видит свои данные (RLS). Выход завершает сессию.
- Пользователь один. Жена в модели не участвует (общий котёл «свои деньги»).

## 1a. Первый запуск (ADR-0008)

- Мастер первого запуска: дата начала учёта (по умолчанию сегодня, потом не меняется), стартовый долг двумя суммами («компания должна мне», «я должен компании», любая может быть 0).
- Затем добавление счетов (см. раздел 2).

## 2. Счета

- Список счетов пользователя: карты, банковские счета, наличные.
- Создание счёта: имя, банк (или наличные), тип, маска, владелец (me/spouse), валюта (по умолчанию KZT), дата старта (по умолчанию сегодня, не раньше даты начала учёта, потом не меняется), текущий остаток «всего на счёте» и «из них компании». Свои показываются как разница. Создаются стартовые корректировки на дату старта.
- Записи раньше даты старта счёта создать нельзя.
- Редактирование: имя, маска, банк, владелец. Валюту менять нельзя, если по счёту есть операции.
- Архив: убирает счёт из активного списка, но сохраняет историю. Разрешён только при нулевом остатке и нулевом авансе.
- Удаление: запрещено при наличии операций. Только архив.
- По каждому счёту видно: остаток, аванс компании, свои деньги (остаток минус аванс).
- Наличные ведутся как счёт. Снятие и возврат нала делаются переводом между картой и наличными.

## 3. Категории

- Список категорий пользователя. Создание, переименование, архив.
- Категория обязательна для траты (expense), опциональна для поступления (income).
- Уникальность имени в рамках пользователя.

## 4. Операции (записи)

Единая сущность с типом. Типы и их эффект на расчёт описаны в доке 03. Здесь поведение ввода и жизненного цикла.

### 4.1. Способы ввода

Кнопка добавления открывает меню из режимов:

1. **Полная запись.** Форма с переключателем типа (трата по умолчанию). Все поля. Статус сразу done.
2. **Быстрый capture.** Только трата. Минимум: сумма, счёт, назначение (личное/работа), короткий текст. Если движку хватает данных для расчёта, запись сразу done (работа на любом счёте; личное на счёте без аванса). Если не хватает (личное на счёте с авансом: непонятно, чьими деньгами), draft с `source_pending = true` в инбокс. Категория необязательна: done без категории учитывается сразу и висит в инбоксе с отметкой «без категории» (ADR-0009).
3. **Заметка.** Текст и/или скрин. НЕ запись. Уходит в раздел заметок со статусом new. На баланс не влияет.
4. **Импорт файла.** Загрузка CSV, Excel, JSON (см. раздел 8).

Связка: из быстрого ввода можно "развернуть в полную", перенеся введённое.

### 4.2. Поля и поведение формы траты (expense)

- Сумма и валюта. При не-тенге открывается блок пересчёта: курс Нацбанка (по умолчанию, на дату), свой курс, или сумма в тенге напрямую. Система показывает тенговый эквивалент.
- Счёт (выбор из справочника, не ввод текста).
- Назначение: личное или работа.
- Источник: спрашивается ТОЛЬКО когда назначение личное и на счёте есть аванс (деньги компании или мои). В остальных случаях выводится автоматически (см. док 03).
- Категория, дата (по умолчанию сегодня), комментарий, вложения (скрытый блок "дополнительно").
- Живой предпросмотр эффекта: до сохранения показывает, что произойдёт с остатком, авансом и долгом. Считает сервер через RPC `preview_entry` (тот же движок, откат транзакции, ADR-0010).

### 4.3. Остальные типы

Поля и эффекты по доку 03: income, transfer, company_topup, company_advance_return, settlement, adjustment, refund. Счета везде выбираются из списка. В переводе "куда" не показывает счёт, выбранный в "откуда" (один и тот же счёт запрещён).

### 4.4. Жизненный цикл записи

- draft → done при разборе в инбоксе (дозаполнение, уточнение источника).
- Правка записи: пересобирает её ledger строки, запускает recompute.
- Удаление: удаляет запись и её ledger строки, запускает recompute. Вложения удаляются каскадом.
- Любое изменение done-записи меняет баланс, поэтому всегда через движок (RPC), не прямым UPDATE с клиента.

## 5. Инбокс

- Список того, что требует разбора: черновики (draft), done-траты без категории и новые заметки (note.status = new).
- Бейдж с количеством.
- Для черновика с `source_pending` подсвечено "источник?". Разбор: открыть, дозаполнить, сохранить (done).
- Для заметки: открыть, создать запись (откроется полная форма с предзаполнением из текста/скрина) или передать Claude Code. После заметка помечается processed.
- Пока элемент в инбоксе, на баланс он не влияет.

## 6. Заметки

- Список заметок: новые и разобранные.
- Заметка = текст и/или скрин. Можно только текст.
- Статус new / processed. У processed видна ссылка на созданную запись.
- Не влияют на баланс никогда.

## 7. Баланс с компанией

- Показывает две стороны (компания должна вам, вы должны компании) и итог после зачёта.
- Раскрытие: каждая сторона разворачивается в список операций, из которых она сложилась (трассировка к конкретным записям).
- Отдельно список взаимозачётов.
- Всё выводится из ledger, не хранится числом.

## 8. Импорт

- Поддержка CSV, Excel (xlsx), JSON по единой фиксированной схеме (совпадает со схемой экспорта, round trip).
- Шаблон и правила доступны из экрана импорта (для CSV схема колонок, для JSON пример и правила). В окружении приложения файл отдаётся на скачивание; в среде, где скачивание недоступно, схема показывается текстом.
- Поток: загрузка файла → валидация каждой строки → предпросмотр (что создастся, где ошибки, где возможные дубли) → подтверждение → создание записей одной транзакцией (атомарно).
- Атомарно, всё или ничего (ADR-0004): если хоть одна строка невалидна или неполна, файл не импортируется целиком, пользователь получает отчёт по строкам, исправляет файл и загружает заново. В draft строки импорта не попадают.
- Дубли определяются по отпечатку и `external_id` (см. док 03, раздел 6). Возможные дубли показываются в предпросмотре, пользователь решает.
- Партия импорта фиксируется в `import_batches` (для идемпотентности и отката).

Схема строки импорта (поля):
`occurred_on, type, account, amount, currency, category, source, purpose, transfer_purpose, to_account, fee, fee_payer, comment, title, external_id`.
Счета и категории сопоставляются по имени (точное совпадение в рамках пользователя); несопоставленные дают ошибку строки.

**Схема файла записей (`expenses`), тикет 17.** Единственное определение в коде: `supabase/functions/_shared/schema.ts` (`ENTRY_COLUMNS`, `amountSign`), им пользуются и экспорт, и импорт. Колонки в этом порядке: 15 полей выше, затем поля типов, появившихся позже:

| Колонка | Значение |
|---|---|
| `occurred_on` | дата записи, ISO `ГГГГ-ММ-ДД` |
| `type` | `expense`, `income`, `transfer`, `company_topup`, `company_advance_return`, `settlement`, `netting`, `adjustment`, `refund` |
| `account` | название счёта (у перевода «откуда»); пусто у взаимозачёта и корректировки стороны долга |
| `amount` | сумма в основных единицах валюты `currency`, ровно два знака через точку, без разделителей, со знаком (правило ниже) |
| `currency` | ISO-код валюты записи |
| `category` | название категории (трата, поступление; у возврата покупки категория траты) |
| `source` | `own` / `company` (трата «личное») |
| `purpose` | `personal` / `work` |
| `transfer_purpose` | `move_own`, `move_company`, `repay_debt`, `take_advance` |
| `to_account` | название счёта «куда» перевода |
| `fee` | комиссия перевода или пополнения: списание, поэтому минус (`-1000.00`); пусто = без комиссии |
| `fee_payer` | `own` / `company` |
| `comment`, `title` | текст |
| `external_id` | ключ идемпотентности: свой у импортированной записи, иначе id записи |
| `settlement_direction` | `i_paid_company` / `company_paid_me` (погашение долга) |
| `adjustment_target` | `balance`, `company_owes_me`, `i_owe_company` (корректировка) |
| `adjustment_mode` | `plug_hidden` / `plug_analytics` |
| `adjustment_affects_advance` | `true` / `false`, только у корректировки остатка («это деньги компании») |
| `parent_external_id` | у возврата покупки `external_id` его траты |
| `rate` | курс: тенге за 1 единицу валюты, точка, без лишних нулей; пусто у тенге |
| `rate_source` | `nbk`, `manual`, `derived`; пусто у тенге |
| `amount_kzt` | тенговый эквивалент, со знаком `amount` |
| `in_analytics` | `true` / `false` |

Пустое значение: пустая ячейка в CSV и xlsx, `null` в JSON. Черновики не выгружаются (импорт их не создаёт). Строки идут в порядке пересчёта (дата, время, создание), поэтому импорт по порядку строк повторяет хронологию.

**Правило знака `amount`.** В базе сумма всегда больше нуля, направление несёт тип. В файле знак = движение денег по счёту из `account`: минус у траты, перевода (уходит с «откуда»), изъятия аванса и погашения «я отдал компании» (`i_paid_company`); плюс у поступления, пополнения от компании, возврата покупки, погашения «компания отдала мне» и взаимозачёта (без счёта, всегда плюс); у корректировки знак суммы и есть знак корректировки (`adjustment_sign`), и для остатка, и для стороны долга. Импорт выводит из знака знак корректировки, у остальных типов знак должен совпасть с правилом, иначе ошибка строки.

**Импорт (тикет 18).** Читает файл `expenses` этой схемы (или zip экспорта целиком): CSV в UTF-8 (BOM пропускается), xlsx (первый лист или лист `expenses`; читает `read-excel-file`, числовая ячейка берётся текстом и округляется до 15 значащих цифр, как её показывает Excel, поэтому `1234.5599999999999` = `1234.56`; дата, набранная датой Excel, читается как ISO), JSON-массив объектов (числа читаются исходным текстом). Обязательны колонки `occurred_on`, `type`, `amount`, остальные можно опустить; колонка не из схемы = ошибка файла. Знак суммы проверяется правилом ниже, у корректировки он становится её знаком; комиссия только с минусом. Счета и категории по точному названию. У личной траты `source` обязателен: импорт не видит аванс, который принесут строки того же файла (пересчёт один раз в конце). Возможный дубль: учтённая запись с тем же отпечатком (тип, счёт, сумма, валюта, заголовок или категория) в окне ±3 дня от даты строки, в том числе строка выше в том же файле; по умолчанию не создаётся, владелец отмечает «Создать всё равно». Повтор `external_id`, который уже есть в базе (в том числе id записи, выгруженной экспортом), пропускается; повтор внутри файла = ошибка строки. Курс Нацбанка для валютных строк с `rate_source = nbk` экран сначала кладёт в кэш через `fetch_rates`.

**Файл `company_settlement`** (только экспорт, импорт его не читает; `SETTLEMENT_COLUMNS`): `occurred_on, type, account, to_account, title, category, purpose, source, transfer_purpose, settlement_direction, currency, company_owes_me_change, i_owe_company_change, company_owes_me_after, i_owe_company_after, net_after, external_id`. Одна строка на запись, двигавшую долг; изменение стороны со знаком (выросла = плюс), стороны после записи считаются по всей истории, даже если период её обрезает; `net_after` = «компания должна мне» минус «я должен компании»; `external_id` связывает строку с записью в `expenses`.

**Форматы.** CSV: UTF-8 с BOM (Excel открывает кириллицу; импорт BOM пропускает), запятая, строки через CRLF, кавычки по RFC 4180. JSON: массив объектов с ключами в порядке схемы, суммы числами с двумя знаками (`-1500.00`), импорт читает их без float (исходный текст числа). Excel (xlsx): даты текстом ISO, суммы числовыми ячейками с форматом `#,##0.00;[Red](#,##0.00)`, `true`/`false` логическими ячейками. Экспорт отдаёт один zip с двумя файлами выбранного формата.

## 9. Экспорт

- Два плоских файла (CSV по умолчанию, также Excel и JSON):
  - `expenses` (операции): все записи с полями для анализа.
  - `company_settlement` (движения с компанией): начисления из операций, пополнения, взаимозачёты, с остатком после.
- Даты в ISO (ГГГГ-ММ-ДД). Суммы в основных единицах с ровно двумя знаками через точку, без разделителей (`1500000.00`), плюс колонка валюты. То же в импорте: разбор строкой в minor, без float; больше двух знаков = ошибка строки (РЕШЕНО).
- Отрицательные суммы (траты, списания, всё что минус) в бухгалтерском формате: не `-1500.00`, а `(1 500.00)` красным.
  - Excel (xlsx): ячейка остаётся числом (отрицательным, чтобы работали формулы), формат ячейки `#,##0.00;[Red](#,##0.00)`, положительные с разделителем тысяч.
  - CSV и JSON: цвета нет, суммы обычным числом `-1500.00` (машиночитаемо, для round trip). Импорт принимает и `-1500.00`, и `(1500.00)` как отрицательное.
- Фильтр по периоду.
- Схема экспорта = схема импорта, чтобы Claude мог сгенерить файл обратно.

## 10. Агрегаты для обзора

Выводятся из ledger:
- Итог с компанией (две стороны и нетто).
- Всего денег на счетах (сумма остатков).
- Свои деньги всего (сумма остаток минус аванс).
- Денег компании на картах (сумма авансов).
- Личные траты за период (сумма трат с назначением personal, учитывая `in_analytics`).
- Остаток и аванс по каждому счёту.

## 11. Claude Code ingestion

- Отдельный защищённый вход, через который Claude Code создаёт записи из разобранных заметок.
- Проходит ту же валидацию и тот же движок, что и обычное создание.
- Токен служебный, хранится как хэш, с возможностью ротации.

## 12. Общие правила поведения

- Все денежные операции идут через RPC-функции, которые валидируют и запускают движок в транзакции. Клиент не делает прямых INSERT/UPDATE в `entries` или `ledger_entries`.
- Любая ошибка операции откатывает всё целиком, баланс не портится.
- Язык интерфейса русский. Валюта по умолчанию тенге.
- Часовой пояс Asia/Almaty (UTC+5): «сегодня» и время из выписок без зоны трактуются в нём.
- Формат сумм на экране везде: пробел между тысячами (неразрывный), запятая перед копейками, копейки только если не нулевые: `1 500 000 ₸`, `1 500,50 ₸`, `$1 200`. В полях ввода разделитель тысяч при наборе, копейки через запятую или точку.
