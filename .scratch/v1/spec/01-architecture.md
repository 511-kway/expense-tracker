# 01. Архитектура

Версия 1. Дата: 2026-11-03.

## 1. Требования к стеку

- Только бесплатные и open source инструменты.
- Self hosted на своём облачном сервере (VPS) под своим доменом.
- База данных Postgres (обязательно).
- Авторизация через Google (Gmail).
- Хранилище файлов для вложений (чеки, скрины, PDF).

## 2. Нужен ли Node

Нет, бэкенд на Node не нужен.

Supabase self hosted закрывает бэкенд целиком без серверного кода на Node:

- **Postgres** это база.
- **PostgREST** автоматически отдаёт REST API поверх таблиц и функций (написан на Haskell, мы его не пишем и не трогаем).
- **GoTrue** даёт авторизацию, в том числе Google OAuth (написан на Go).
- **Storage** хранит файлы вложений.
- **Realtime** (опционально) для живых обновлений, в MVP не обязателен.

Вся бизнес-логика расчёта это **функции Postgres (plpgsql)**, вызываемые как RPC. Никакого отдельного приложения-сервера.

Доп. логику, которой мало (разбор импортируемого файла, подтягивание курса Нацбанка, приём записей от Claude Code), делаем на **Supabase Edge Functions**. Они исполняются на **Deno (TypeScript)**, а не на Node.

Где Node всё же появляется: только как dev-инструмент сборки фронтенда (npm/pnpm и vite для React или Svelte). Это инструмент разработки, а не рантайм-сервер в проде. В самом развёрнутом приложении процесса Node нет.

Вывод для агентов: не поднимать NestJS, Express, Fastify и т.п. Логика в SQL-функциях и Edge Functions. Классический Node-бэкенд допустим только если заказчик явно потом попросит, в MVP его не делаем.

## 3. Компоненты и как они связаны

```
Браузер (веб кабинет, React или Svelte)
        |
        |  HTTPS (JWT пользователя после входа через Google)
        v
  Supabase (self hosted, Docker)
   ├── GoTrue        авторизация, Google OAuth, выдача JWT
   ├── PostgREST     авто REST API к таблицам и RPC-функциям
   ├── Storage       вложения (чеки, скрины, PDF)
   ├── Edge Functions (Deno)  импорт, курсы Нацбанка, ingestion от Claude Code
   └── Postgres
        ├── таблицы (см. док 02)
        ├── RLS     изоляция данных по пользователю
        └── функции (plpgsql)  движок расчёта, recompute, create/edit/delete операций
```

Claude Code работает вне приложения: разбирает заметки с фото в нормальные записи и пишет их в ту же базу через PostgREST или через Edge Function приёма (см. ниже).

## 4. Фронтенд

- React + Vite + TypeScript (решено, ADR-0005).
- Общается с бэкендом через supabase-js (клиентская библиотека Supabase): авторизация, запросы к таблицам, вызов RPC, загрузка файлов в Storage.
- Фронт НЕ содержит бизнес-логики расчёта. Он только собирает ввод, зовёт RPC-функции и показывает результат. Это важно: единственная правда про деньги живёт в Postgres.

## 5. Авторизация (Google)

- Через GoTrue с провайдером Google OAuth.
- Пользователь жмёт "Войти через Google", проходит OAuth, получает JWT. JWT уходит с каждым запросом.
- В Postgres включён RLS. Каждая таблица с пользовательскими данными фильтруется по `user_id = auth.uid()`. Пользователь видит и меняет только свои строки.
- MVP однопользовательский по смыслу (владелец и жена под одним аккаунтом владельца). Но `user_id` закладываем на каждую строку сразу, чтобы потом не переписывать.
- Настройка Google OAuth: создать OAuth client в Google Cloud Console, прописать redirect URL Supabase, задать client id и secret в конфиге GoTrue. Это делается руками при деплое, в коде не хранится.

## 6. Хостинг и деплой

- VPS в облаке (у владельца уже есть сервер).
- Docker и docker compose: поднимается стандартный self-hosted Supabase (официальный compose-набор) плюс контейнер статики фронта.
- Обратный прокси **Caddy**: терминирует HTTPS, бесплатный сертификат через Let's Encrypt (автоматически), раздаёт фронт и проксирует запросы на Supabase.
- Домен: отдельный DNS (например, `money.example.com` или поддомен выбранного домена). A-запись на IP VPS. Можно бесплатный поддомен (DuckDNS), но обычный домен удобнее для Google OAuth redirect.
- Переменные окружения и секреты (ключи Supabase, Google client id/secret, ключ к курсам, токен ingestion для Claude Code) в `.env` на сервере, НЕ в репозитории. В репо только `.env.example` с пустыми значениями.

## 7. Безопасность

- RLS на всех пользовательских таблицах. Без исключений.
- Edge Functions, которые пишут в базу (импорт, ingestion), проверяют пользователя по JWT или по отдельному серверному ключу с ограниченной областью.
- Токен для Claude Code ingestion хранится как ХЭШ (SHA-256) в базе, не открытым текстом, на случай слива. Плюс срок и возможность ротации.
- Денежные RPC-функции выполняются как единая транзакция. При любой ошибке откат целиком.
- Никаких денежных вычислений на клиенте: клиент может только предлагать, база считает и проверяет.

## 8. Внешние интеграции

- **Курсы валют: Нацбанк РК.** Открытые дневные курсы (XML/RSS по дате). Edge Function `fetch_rates` тянет курс на дату операции и кладёт в таблицу `fx_rates` (кэш). Если курса на дату нет или сервис недоступен, пользователь вводит курс или тенговую сумму вручную (см. док 03, валюта).
- **Claude Code ingestion.** Отдельный защищённый вход (Edge Function или RPC под служебным токеном), через который Claude Code создаёт записи из разобранных заметок. Проходит ту же валидацию и тот же движок, что и обычное создание.

## 9. Среды

- `local` для разработки (Supabase локально через CLI).
- `prod` на VPS.
- Хостед тестовой среды в MVP можно не делать, но схема и миграции должны разворачиваться одной командой на чистой базе.

## 10. Миграции

- Все изменения схемы через SQL-миграции (папка `supabase/migrations`), применяются Supabase CLI.
- Функции движка (plpgsql) тоже в миграциях, версионируются.
- Чистая база плюс миграции плюс сиды (справочники счетов и категорий владельца) дают рабочее приложение одной командой.
